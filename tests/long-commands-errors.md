Run `sh tests/long-commands-errors.sh` on a Mac with Swift 6.4 or later. An optional argument selects an earlier `ExecuteLongCommandIntent.swift` for the RED comparison.

The harness calls the production intent's `perform()` and checks the thrown error descriptions for an extension with no enclosing `.app` and for a failed shared-container lookup. A failed `Bundle(url:)` must still succeed: with a real `.app` directory with mode 311 (traversable, not listable), where Foundation's `Bundle(url:)` returns nil, the fixture takes `APPNAME` and `APPVERSION` from the `Info.plist` and reads its resources from the app directory; with no readable `Info.plist`, `APPNAME` is the directory name and `APPVERSION` stays unset. Successful fixtures check the returned `APPDIR` and `APPNAME`. Bundle lookup and FileManager container failures are injected at OS boundaries; successful bundle lookups use Foundation. A detached extension uses Foundation without bundle-failure injection and must report its starting bundle path. AppIntents scheduling, ios_system execution and UIKit's device model are substituted. These are host regression checks; Shortcuts registration and device execution require separate checks.

## Bundle layout evidence

Checked on 2026-11-08 against the project and Xcode 27.2's `PackageTypes.xcspec`. The project embeds LongCommands with `dstPath = "$(EXTENSIONS_FOLDER_PATH)"`. Xcode defines `EXTENSIONS_FOLDER_PATH` as `$(CONTENTS_FOLDER_PATH)/Extensions` and `PLUGINS_FOLDER_PATH` as `$(CONTENTS_FOLDER_PATH)/PlugIns`. For shallow iOS bundles, `CONTENTS_FOLDER_PATH` is the `.app` itself; for native macOS and Catalyst bundles it is `.app/Contents`.

| Platform or fixture | Extension bundle relative to the app | Evidence and limits |
| --- | --- | --- |
| iPhone/iPad | `a-Shell.app/Extensions/a-Shell-LongCommands.appex` | Project copy phase and Xcode shallow-bundle definitions. Both full and mini LongCommands targets use the same source; the mini extension is named `a-Shell-mini-LongCommands.appex`. |
| iOS app on Apple silicon Mac | Inner `a-Shell.app/Extensions/a-Shell-LongCommands.appex`, including when nested under an outer `Wrapper.app/Wrapper/` | The project builds iOS targets with Catalyst disabled. Wrapping an iOS app does not add `Contents` inside its bundle. The harness checks nested app selection using `PlugIns`; it does not establish the installed reporter's path or Mac execution. |
| `PlugIns` container | `a-Shell.app/PlugIns/a-Shell-LongCommands.appex` | Xcode's plug-in directory convention. Covered as a fixture; LongCommands currently uses `Extensions`. |
| Native macOS or Catalyst bundle | `a-Shell.app/Contents/Extensions/a-Shell-LongCommands.appex` or `Contents/PlugIns/a-Shell-LongCommands.appex` | Xcode deep-bundle definitions. Portability fixtures only: a-Shell currently disables Catalyst and does not build a native macOS LongCommands target. |
| App as main bundle | `a-Shell.app` | Defensive fixture. Foundation defines `Bundle.main` in terms of the current executable; no runtime path from the Discord report is available. |

The lookup starts at `Bundle.main.bundleURL` and selects the nearest enclosing `.app`, including the starting bundle itself. When `Bundle(url:)` fails for that app, `Info.plist` is read by path (the directory name gives `APPNAME` if it is unreadable) and the app directory is the resource path (the flat iOS layout). It stops at the filesystem root if no app encloses the extension, and includes the starting path in its error. It does not search for unrelated installed apps. The flat and wrapped iOS fixtures already pass with the old two-parent lookup; the app-main, deep-bundle and detached fixtures fail with that implementation.

The [Discord report relayed on #1155](https://github.com/holzschu/a-shell/pull/1155#issuecomment-6719721378) contains only the error text, without a device, OS version or installation source. The maintainer separately confirmed a Mac crash on macOS 26. Neither observation identifies the failing bundle layout.

Foundation reference: [`Bundle.main`](https://developer.apple.com/documentation/foundation/bundle/main). Apple's [bundle structure guide](https://developer.apple.com/library/archive/documentation/CoreFoundation/Conceptual/CFBundles/BundleTypes/BundleTypes.html) documents flat iOS application bundles and macOS `Contents` bundles.
